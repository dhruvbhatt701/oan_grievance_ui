# Grievance Management Portal

A grievance-intake and case-management dashboard for Ethiopia OpenAgriNet. Next.js 16 (App Router, Turbopack), Redux Toolkit for client state, Tailwind v4. There is no local database or ORM — every real read/write goes through `oan_auth_service` (auth) and the wider OpenAgriNet backend (grievance data), reached only from server-side code.

## Auth & session architecture

Sessions are three httpOnly cookies (access token, refresh token, remember-me flag) plus an idle-activity cookie — never a token in `localStorage` or client state. Start at `src/lib/session.ts` (the single place cookies are written/cleared) rather than re-deriving this from each route:

- `src/proxy.ts` — the route guard (Next 16 renamed `middleware` to `proxy`; see `AGENTS.md`). Decodes (not verifies) the access token to route protected vs. public pages, and stamps every response with a per-request CSP nonce.
- `src/lib/session.ts` — session cookie read/write/clear.
- `src/lib/idleSession.ts` / `src/lib/idleTimeoutConfig.ts` — the idle-timeout clock (`/api/auth/heartbeat` and the client `useIdleTimer` hook slide it forward). Enforced at every entry point that accepts a session cookie, not just `src/proxy.ts` — `proxy.ts` excludes `/api/*` from its matcher (a redirect doesn't make sense for an XHR/fetch call), so `/api/proxy/[...path]`, `/api/auth/me`, and `/api/auth/refresh` each check `isSessionIdleExpired` (`activeSession.ts`) themselves too. `/api/proxy/*` is the one that matters most in practice: it's every real data call this SPA makes.
- `src/lib/jwt.ts` — decodes the access token's claims for display/routing only; the backend is what actually verifies it.
- `src/lib/rateLimit.ts` — in-memory, per-process rate limiting for the `/api/auth/*` routes.
- `src/app/api/proxy/[...path]/route.ts` — the one path all non-auth backend calls go through, so the browser only ever talks to same-origin `/api/*`.
- `src/lib/realtime/` + `realtime-gateway/server.ts` + `src/app/api/realtime/config/route.ts` — the socket.io client for `oan_grievance_service`'s AsyncAPI events (`attachment_scanned`, `notification`). A browser connects to the same-origin gateway on port 3001, which checks the idle cookie and translates the `auth_token` cookie into an `Authorization: Bearer` header before forwarding to Frappe. Events are signals: listeners refetch through `/api/proxy`, and a local `resync` event fires on reconnect and tab focus because missed events are never replayed.
- `src/features/auth/logout.ts` — `performLogout`, the single way a session ends client-side (revokes server-side, then resets Redux). Anything that signs the user out — the header's Sign Out button, the idle timer — goes through this rather than reimplementing it, and awaits it before navigating: a fire-and-forget logout races the next page's session-restore check.
- `src/app/api/auth/set-initial-password/route.ts` + `src/features/auth/components/SetInitialPasswordModal.tsx` — an admin-created officer's first sign-in. `POST /api/v1/auth/login` answers `403 PASSWORD_CHANGE_REQUIRED` (not the generic invalid-credentials message — see `login/route.ts`'s own branch) when the password is correct but still the one an admin typed for them (`CreateOfficer.temporary_password` / `POST /api/v1/officers/:officer/password-resets` in `oan_grievance_service`). `LoginForm` detects that distinct message and opens this modal, which is guest-reachable (no token — the temporary password itself proves identity) and sets no session cookies: the officer signs in fresh afterwards.
- `src/lib/iamSession.ts` + `src/lib/activeSession.ts` + `src/app/api/auth/staff/{login,complete,callback}/route.ts` — "Sign in as staff", delegated to the OpenG2P IAM service (the registry-hub pattern from `openg2p-developer/docs/staff-portal-login-flow.md`). The browser never calls IAM's API (only its OAuth callback, as in the hub): `/api/auth/staff/login` opens IAM's login transaction server-to-server (with an absolute `redirect_uri` back to `/api/auth/staff/complete`, as the hub passes its own page URL) and redirects to Keycloak; Keycloak returns to IAM's own callback, which sets IAM's cookies and redirects to `/api/auth/staff/complete`, which starts the idle clock. Optionally `/api/auth/staff/callback` can stand in for IAM's callback (set it as the login-provider row's `oauth_callback_url`) to keep IAM entirely out of the browser. That session is IAM's cookies (`X-Access-Token`, `X-Session-Id`, … on the shared parent domain) — never copied into `auth_token`. `activeSession.ts` hides the two session kinds behind one shape for the proxy, `/api/auth/{me,refresh,logout,heartbeat}` and realtime config; IAM tokens are renewed by calling IAM's `get_user_profile` (IAM has no refresh endpoint — its middleware refreshes on any authenticated route). Logout revokes at IAM, then takes the Keycloak logout URL from IAM's own logout redirect, swaps its `post_logout_redirect_uri` for this app's login page, and `performLogout` navigates the browser there — so the Keycloak SSO session ends too, with no Keycloak details configured here. That return URL must be on the Keycloak client's redirect allow-list. `oan_auth_service` verifies these tokens by asking IAM (`api/iam_tokens.py`) and syncs roles from `resource_access[IAM_APPLICATION]`. An IAM session is single sign-on, so it need not have been opened here: one opened at the registry is adopted as-is (`readActiveSession`), as long as the user holds a role on `IAM_APPLICATION` (`hasAppAccess`; otherwise they are a guest here and `/api/auth/staff/complete` answers `?reason=staff_no_access`). This app's idle clock applies to local sessions only (`isSessionIdleExpired`) — IAM's idle timeout is Keycloak's — and an idle kick clears only local cookies (`clearIdleSessionCookies`), never IAM's, which would sign the user out of the registry too.

## NGO / FPO organisation onboarding

NGO and FPO representatives register through the ordinary `/register` flow — the profile step asks only for the representative's Fayda ID (plus the ID consent) and registers with `submitter_type: "NGO" | "FPO"` and `fayda_id` — no `registration_number` — and at their first sign-in land on `/ngo` or `/fpo` instead of Submit Grievance to "Complete Registration" — until the organisation is registered; from then on they sign in straight to Submit Grievance (the "My Organisation" sidebar item leads back to the status screen). Submitting that form redirects to `/submit-grievance`, which pre-fills from `/auth/me`. Both routes render `src/features/organisation/components/OrganisationPage.tsx`: the "Register your organisation" form until `GET /api/v1/orgs/me` returns an organisation, then its In Review / Active / Suspended status. That form asks for Organisation Name, Registration Number and Authorised Representative (all required), plus Member Count Affected on `/fpo` only (sent as `members_affected`), alongside the address and contact cards. In the address card, Region, Zone, Woreda and Kebele are cascading dropdowns (`OrganisationAreaFields.tsx`, built on `useAreas` like Submit Grievance's location fields): each lists the areas under the one chosen above it, and `POST /orgs` still receives the chosen areas' *names* in `region`/`zone`/`woreda`/`kebele`. Kind-specific differences (organisation type, entity types) live in `src/features/organisation/config.ts`.

- The JWT carries roles only, so `proxy.ts` cannot tell NGO from FPO (both are plain Submitters). The landing route is picked at sign-in by `homeRouteForUser` (`features/auth/rbac.ts`) from `organisationKindOf` (`lib/organisationKind.ts`), i.e. the backend profile `type` from `/auth/me`. The backend records NGO/FPO at sign-up, so this is known from the first sign-in, on any browser — nothing is kept in localStorage for it. Once the organisation is registered (`user.organisation`, from `profiles.grievance.organization`) `LoginForm` passes that to `homeRouteForUser` and the representative lands on Submit Grievance like any other submitter, whatever the organisation's status (that page shows the verification notice and blocks filing via `can_file`). Only `LoginForm` knows the organisation: `proxy.ts` and the staff sign-in route route from JWT roles alone via `homeRouteForRoles`, and if `/auth/me` fails right after login the representative falls back to `/ngo` or `/fpo`, where the status screen and sidebar are still available.
- The screen talks to `oan_grievance_service`'s `/api/v1/orgs` endpoints through `/api/proxy` (contract: that repo's `docs/organization-registration-api.md`): `GET /orgs/me` (404 until registered) and `POST /orgs` (answers with the record, status `In Review`; requires `consent_given: true`, which the form's checkbox gates). The onboarding form's registration number starts from the one given at sign-up. The request body is built in one place, `toRegistrationPayload` in `organisationApi.ts`; the registration number is sent as `registration_number` (the backend dropped the `tax_registration_number` alias and refuses unknown keys), and error shapes (400 `details`; the plain-message 400s "Registration Number must be unique" and "Representative Account must be unique", which `duplicateRegistrationOf` tells apart; 403) are handled in `OrganisationRegistrationForm.tsx`. Once registered, `/auth/me` also carries `profiles.grievance.organization` (status, `can_file`, ...), which Submit Grievance reads. The admin verification endpoints (`GET /orgs`, `PATCH /orgs/{id}/status`) have no UI yet.

## Dashboard

`src/features/dashboard/` renders the landing page from one request, `GET /api/v1/charts?charts=grvKpis,grvStatusDistribution,grvByCategory,grvMonthlyTrend` (via `/api/proxy`). The service narrows counts to an officer's own desks and returns everything to an admin, so nothing in the UI filters by role; a 403 shows the "forbidden" message.

- `api/dashboardApi.ts` parses each chart with its own Zod schema; a chart that is `null`, missing or in an unknown shape becomes `null`, never zeros. If every chart is `null` the page shows its error state.
- `utils/mapDashboardCharts.ts` turns the parsed charts into what the components draw. `null` means "unavailable" and renders as a retryable section, which is different from an empty list.
- Recent Grievances (`src/app/(dashboard)/dashboard/components/`) reads the All Grievances list on its own, so it still renders when the statistics fail.
- All copy is in `messages/*.json` under `dashboard.*`; `messages.test.ts` fails if a locale is missing a key. Backend status labels are translated when known and shown as sent otherwise.

## Required environment variables

| Variable | Required | Default | Purpose |
| --- | --- | --- | --- |
| `AUTH_API_BASE_URL` | Yes | — | Base URL of `oan_auth_service` (see `src/lib/env.ts`) |
| `TRUSTED_PROXY_HOPS` | No | `0` (don't trust `X-Forwarded-For`) | Reverse-proxy hop count for client-IP resolution |
| `RATE_LIMIT_<LOGIN\|REGISTER\|REGISTER_SHARED\|REFRESH\|LOGOUT\|HEARTBEAT\|FORGOT_PASSWORD\|RESET_PASSWORD\|SET_INITIAL_PASSWORD\|REALTIME_CONFIG\|STAFF_LOGIN>_MAX` / `_WINDOW_MS` | No | see `rateLimit.ts` | Per-route rate-limit overrides. `REGISTER_SHARED` is the effective ceiling for `/api/auth/register` whenever `TRUSTED_PROXY_HOPS` is unset — see that route's own comments. `SET_INITIAL_PASSWORD` guards `/api/auth/set-initial-password`, where an officer replaces an admin-issued temporary password (`oan_auth_service`'s `POST /api/v1/auth/password/initial`) |
| `IDLE_TIMEOUT_MS` / `IDLE_WARNING_LEAD_MS` | No | 15 min / 60 s | Server-enforced idle-session cutoff and warning lead — local (email/password) sessions only; IAM sessions use Keycloak's idle timeout |
| `NEXT_PUBLIC_IDLE_TIMEOUT_MS` / `NEXT_PUBLIC_IDLE_WARNING_LEAD_MS` | No | same as above | Client copies — set alongside the two above if you override them, or the warning modal drifts from the actual cutoff |
| `IAM_BASE_URL` | No | unset (staff sign-in off) | OpenG2P IAM service, server-only. Requires the next two |
| `IAM_LOGIN_PROVIDER_ID` / `IAM_APPLICATION` | With `IAM_BASE_URL` | — | IAM login-provider row id; Keycloak client whose roles count (must equal `oan_auth_service`'s `iam_application`) |
| `IAM_COOKIE_PREFIX` / `IAM_COOKIE_DOMAIN` | No | `''` / host-only | Must match IAM's `*_AUTH_COOKIE_PREFIX` / `*_AUTH_COOKIE_DOMAIN`. Prefix: to find IAM's cookies by name. Domain: only to expire them once IAM refuses to renew the session |
| `REALTIME_PUBLIC_URL` / `REALTIME_GATEWAY_PORT` | No | unset (realtime off) | The URL the browser connects to for sockets (e.g. gateway at `http://localhost:3001`), and the port the gateway binds to. |
| `REALTIME_UPSTREAM_URL` / `REALTIME_SITE` | No | `ws://localhost:9000` | The backend socket.io origin the gateway proxies to, and the Frappe site name used for the namespace. |
| `REALTIME_UPSTREAM_IS_FRAPPE` / `REALTIME_PATH` | No | `false` / `/socket.io/` | Whether to inject Frappe-specific headers (`x-frappe-site-name`, overwrite Origin) and the socket path. |
